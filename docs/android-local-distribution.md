## Exact owner checkpoint: permanent signing (phone browser)

No private signing material has been generated by the agent. The permanent key
must first exist under the owner's control with durable backups. Do not send its
password, keystore, base64 or any private key to ChatGPT.

1. In the phone browser open this branch in GitHub. `Code` → `Codespaces` → create
   a codespace on this branch, using the smallest machine. Use Chrome's Desktop
   site option if the mobile layout hides these controls. Codespaces has an
   included personal-account quota; do not enable paid overage for this task.
2. Open `Terminal` → `New Terminal`. Run `bash scripts/setup-permanent-signing.sh`.
   If prompted, complete GitHub's browser/device login as the repository owner.
3. Enter a strong NEW signing password privately in the terminal (input is hidden),
   and retain it in a password manager. Script creates the permanent PKCS12 key
   with alias `salary-distribution`, RSA 3072, long validity; re-runs reuse it.
4. When the script pauses, use Explorer → `signing-private` → long-press/right-click
   `salary-distribution.p12` → Download. Preserve two protected copies outside
   Codespaces and keep the password separately. The directory is gitignored.
5. Only then type `BACKED-UP` in the terminal. The script sets encrypted GitHub
   Actions secrets directly using stdin: ANDROID_KEYSTORE_BASE64,
   ANDROID_STORE_PASSWORD, ANDROID_KEY_PASSWORD, ANDROID_CERT_SHA256. Nothing is
   printed except the public certificate fingerprint. Source/Actions artifacts
   must NEVER contain signing files. Existing signing secrets block accidental
   regeneration if the local key is missing.
6. Return to this session and say the signing setup finished. The agent reruns the
   existing distribution workflow at the reviewed commit and inspects its results.
   Stop the codespace after setup to avoid consuming time; delete it only once
   backups are preserved. No desktop computer or new repository is needed.

If the included Codespaces quota is unavailable or keytool/gh is missing, stop
at that specific step; do not enable billing or create a second signing identity.

## CI and real A→B gate

`android-distribution.yml` validates the required debug Work* suite/preview plus
release Work* suite, unsigned release compilation, release instrumentation
compilation, package/config gates. AGP's release unit-test restriction is disabled
explicitly. Without owner signing secrets this is **not an installable RC**.

With secrets, build-release-candidates.sh builds A at the distribution source
versionCode (initially 6) and B at source+1 (initially 7), both real non-debuggable
release builds with the same permanent key. Public certificate fingerprint must
match the pinned fingerprint secret. No debug fallback or temporary key exists.

A disposable API 35 emulator installs A, then the equally signed test APK. Tests
seed mixed currencies, manual/range/group entries, breaks, notes, custom rates,
paid/unpaid, workers, categories and local defaults. Airplane/offline execution,
force-stop/restart, exact backup and journal snapshot comparison, then `adb install
-r candidate-b.apk`, verify unchanged rows/settings/identities, edit and backup.
No uninstall, data clear, destructive migration or real phone access is used.
The signed candidate artifact is uploaded only if the update gate passes.

Evidence includes source SHA, exact package/version, public certificate fingerprint,
APK SHA-256, JUnit reports, three instrumentation stages, install output and crash
log. Failure evidence never contains user data or signing secrets. This tests
package updates using a real release; it does not prove the user's physical device,
installer permission flow, real GitHub update download or actual preview backup.

## Preview → permanent app migration

Do not uninstall or clear either original/preview app. First finish any active
preview shift and export its full JSON backup to a location outside the app. If

After signed RC review: install permanent package side by side, open Settings,
import the JSON, inspect the validation summary, then confirm. Compare all fields
and currency-separated totals; restart and compare again; export from the new app.
Repeat import should add zero. Keep the preview and source backup until the owner
has verified success. Unknown/missing preferences may require manual selection;
preview category format only has name/rate and does not export all settings.

## Future stable releases (only after owner review)

1. Edit Android code, increase distribution source versionCode beyond every prior
   delivered candidate (initial B consumes 7, so next source must be >=8); edit
   versionName. Original/preview versions stay independent.
2. Push the distribution branch, or run the reviewed workflow after it reaches
   the default branch in a later approved merge. No merge is performed now.
3. Inspect unit/build/update evidence and visually review candidate B. Retain prior
   installable APK + report so future schema upgrades can also test the actual
   previous public binary, not just same-source A/B.
4. With explicit public-release approval, download/rename the verified B APK,
   prepare notes and run scripts/prepare-release-manifest.py with --apk, --tag,
   --notes. This only writes local release.json. Check its hash matches CI.
5. Manually create a GitHub Release with that APK, notes and release.json. Only a
   reviewed stable release becomes Latest. RC artifacts remain Actions artifacts,
   never the stable update feed. GitHub web UI can handle ordinary releases on a
   phone; signing is automatic. No publishing workflow currently has write access.
6. Existing users see the next stable version, allow installs from this app when
   Android requests it, then confirm in Android's normal package installer.

No initial public release exists from this work. Before one exists the stable
manifest returns 404 and the app reports no stable update. End-to-end updater
verification remains a gate after private candidate testing and before publication.
